# 3. The smallest law

*Draft 1, the author session, 3 November 2026. Provenance tags as `plan.md` §2; the record is `renavondata/jack` at `6ebea1a` (2026-11-03T05:35Z). The kernel quoted is the one at that commit, 450 lines by `tools/count_kernel.py`; appendix A will carry it whole.*

## 3.0 What this chapter does

Chapter 2 argued that a legal system needs exactly three secondary rules and that each must be code at a seam the agent cannot cross. This chapter reads that code. It takes the record as it is — the shape of an entry, the chain, the signature — and then the three rules in the order Hart gives them: recognition, which is the validity predicate; change, which is keys and amendments; adjudication, which is the judge. It then shows the four maxims of the charter as the mechanisms they became, and ends with the part of the argument a reader should find most persuasive, because it is the part that was not designed: the law changing under itself, five times in seventeen days, each time by its own procedure, each time because the record had shown the text wrong.

The chapter is deliberately close to the code. Where a sentence of the charter is enforced by a function, the function is named; where it is not yet enforced, the chapter says which layer it waits for, as the charter does. The purpose is not to document the kernel — `SPEC.md` does that, to the byte — but to let a reader check the claim of chapter 2 §2.11 without taking it on trust: that a kernel of this size holds the three rules, and that nothing else is in it.

## 3.1 The record

An entry is one line of `log.jsonl`: a JSON object with exactly seven members, `seq`, `parent`, `ts`, `type`, `proposer`, `body` and `sig` [SPEC §4; `kernel/log.py:TOP_KEYS`]. The line is the entry: not a parse of it, not a pretty-printing, the bytes. For that to be a sound statement the serialisation has to be unique, so the record admits exactly one — keys sorted by code point, no whitespace, ASCII only with every other code point escaped as four lowercase hex digits, integers only within ±(2⁵³ − 1), nesting at most thirty-two deep [SPEC §2]. The kernel's whole test of canonicity is one comparison: re-serialise the parsed object and compare it with the line [`kernel/log.py:parse_line`, `canonical`]. Anything that fails is `not_canonical`; anything that is not an object, nests too deep or carries a lone surrogate is `malformed_json`, and the second verdict outranks the first so that two checkers cannot disagree about a line with both defects [SPEC §2, order of checks; §12.15].

The chain is SHA-256 over those bytes. The `parent` of entry *i* is the hash of line *i* − 1 and the `seq` of entry *i* is *i* [SPEC §3; `kernel/log.py:line_hash`]; genesis has sixty-four zeros for a parent [`GENESIS_PARENT`]. Two consequences follow without further rules. An edited line fails at that line, because its signature no longer verifies; an edited and re-signed line fails at the next line, because the next line's `parent` no longer matches; and a second entry on the same parent is the same failure, so forks and rewrites are refused by the same two checks [SPEC §12.8; CHARTER §9, pins `history_rewritten` and `fork_admitted`]. The record is append-only not because a rule says so but because any other operation on it produces a prefix that no longer verifies.

The signature is an SSHSIG blob — the format `ssh-keygen -Y sign` produces — over the canonical line without its `sig` member, in a fixed namespace, `core-entry` [SPEC §6; `kernel/sig.py:NAMESPACE`]. Three decisions about it are worth a reader's attention because they are where a first draft went wrong and a review caught it [REPORT.md §4, as transcript]. The reserved field of the blob must be empty: OpenSSH signs over an empty field whatever the blob carries, so without the rule one signature would have many valid encodings and a line could be re-encoded while staying valid [SPEC §6, decision; §12.5]. Verification is in the kernel, in the standard library, by a strict rule — *S* < *L*, canonical encodings of the public key and of *R*, the cofactorless equation — and `ssh-keygen` is the signing tool and a test oracle, never part of the trusted base [SPEC §6; §12.2; `kernel/sig.py:ed25519_verify`]. And a public key is refused at declaration if its encoding is non-canonical or its point has small order, because a small-order key is an identity anyone can sign for [SPEC §6, weak keys; `kernel/sig.py:weak_key`; REPORT.md §4.4]. The two places where the kernel is stricter than `ssh-keygen -Y verify` are named and tested [`tests/vectors/ssh_keygen_differences.json`]; the kernel follows its own rule, not the tool's.

That is the record: seven members, one serialisation, a hash chain and a signature with one encoding. Everything the law does, it does to lines of this shape.

## 3.2 Recognition — the validity predicate

Recognition is the function `check_entry` in `kernel/check.py`, forty-six lines, called once per line by `check`, which folds the log from an empty state and returns the first refusal or the count [`kernel/check.py:check`, lines 103–111]. The state it folds is ten things [`kernel/check.py:State`]: the head hash; the keys, each a principal, a public-key blob and a set of powers; the owners, a map from blob to key id for the life of the log; the promulgated charter; the amendments with their heights; the trusted base in force; the transmuted set; the forecasts, seq to proposer; the resolved seqs; and the previous entry's timestamp. Nothing else is state, and the charter in force at any position is computable from it [`State.charter_at`].

The predicate runs in a fixed order, and the first failure decides [SPEC §8]. The order is not incidental: it determines which of two defects a line is refused for, and the two checkers must agree on that, so the order is part of the law.

| step | check | reason | where |
|---|---|---|---|
| 1 | the line parses as a canonical JSON object | `malformed_json`, `not_canonical` | `log.py:parse_line` |
| 2 | exactly the seven members, each of the right shape; `ts` a real UTC instant in ASCII digits | `schema` | `log.py:check_shape`, `instant` |
| 2a | `ts` not earlier than the previous entry's (genesis exempt) | `ts_decreased` | `check.py` line 59 |
| 3 | `seq` equals the line's index | `bad_seq` | line 61 |
| 4 | `parent` equals the head | `parent_mismatch` | line 63 |
| 5 | `genesis` at line 0 and nowhere else | `genesis_misplaced` | line 65 |
| 6 | `proposer` not empty | `no_proposer` | line 67 |
| 7 | the body has its type's required members; an `amend`'s id unused and its height above its seq; a `forecast`'s `resolves_by` not before its `ts`; a `resolution`'s forecast recorded and unresolved | `schema` | `log.py:check_body`; `check.py` lines 71–76 |
| 8 | the signature: an exact SSHSIG container; a declared key; that key's principal is the proposer; the type is in the key's powers; Ed25519 verifies | `bad_signature`, `unknown_key`, `proposer_mismatch`, `no_power`, `bad_signature` | `check.py:signer` |
| 8a | a `resolution` is not by its forecast's principal | `self_judged` | line 82 |
| 9 | the entry's effect on the state: a `key` declared, re-declared or revoked (a weak or already-owned public key, or the last `key` power lost, refused); an `amend` promulgated and scheduled; a `push` installed; a `transmute` recorded; a forecast or resolution recorded; the timestamp carried | `bad_key` | `check.py:declare`; lines 84–99 |
| 10 | the head becomes the line's hash | — | line 100 |

Fourteen reason codes, a closed set [`kernel/log.py:REASONS`; SPEC §9]; the verdict is one JSON object, `{"ok":true,"entries":N}` or `{"ok":false,"seq":n,"reason":…,"detail":…}`, and `detail` is free text that the two checkers are never compared on [SPEC §9, §9a.4].

Three things in this order carry law in them. First, the signature is checked *after* the body's schema, so that a resolution of an unresolved forecast by a stranger is `schema` and not `unknown_key`; and `self_judged` is checked after the signature, so that the party is a verified fact before it is judged against — "so that two keys of one party cannot launder a judgement", and a self-resolution with a bad signature is refused for the signature [SPEC §7, forecasts; CHARTER A3.3]. Second, the keys used to verify entry *i* are the keys *before* entry *i*'s own effect: `signer` reads `state.keys` and only afterwards does `declare` run, so a key declared at *i* does not sign *i*, and a revocation at *j* never reaches an entry before *j* [`check.py` lines 77–85; LAW.md §2.2]. That is prospectivity — Fuller's third principle and the charter's second maxim — as a line order rather than a rule, and it is why no pin for `final_law_for_all` was needed at C0: there is no site a mutant could edit to make later law reach back [REPORT.md §4.10]. Third, genesis certifies itself: for line 0 the keys are those its own body declares, registered in array order before its signature is checked [SPEC §7; `check.py` lines 78–80]. The record has one root of trust and it is the line the sovereign signed [seq 0].

What recognition does *not* do is as much the law as what it does. It reads no clock — `ts` is a field, and only its order is checked [SPEC §4]. It reads no file but the log, makes no network call and runs no model [CHARTER §9, refusal list; the second checker's notes say the same of itself, `kernel2/NOTES.md`]. It reads no member of a body beyond the required ones: `forecast.type`, `forecast.args`, `push.record` are optional members the tools read and the kernel ignores, and "a body schema never gains a required member", because a member required today would refuse the entries of yesterday [SPEC §5]. And it judges no merit: a `proposal` and a `merge` have no effect on the state beyond the head and the timestamp [SPEC §8 step 9]. The whole of what the kernel knows about the world is that forecasts exist and get resolved once.

## 3.3 Change — keys, and the law amending itself

Hart's rule of change is the one that makes a system of rules something other than a custom. In jack it has two parts, because there are two things that change: who may act, and what the law says.

**Who may act** is a key with powers. A key declaration names a key id, a principal, a public key and a list of entry types the key may sign [SPEC §5, key declaration; `kernel/log.py:KEY_DECL`]. Genesis declares the first keys; a `key` entry, signed by a key holding the `key` power, declares another, re-declares one — the latest declaration of a key id wins, so a re-declaration can change the principal or the powers — or revokes one by declaring it with empty powers [SPEC §7; `check.py:declare`]. Three constraints are in the kernel and nowhere else. One public key is one identity for the life of the log: a blob once declared under a key id may never be declared under another, even after revocation [`check.py` line 50]. A weak public key is refused [`check.py` line 48]. And the power to declare keys cannot be lost: a `key` entry that would leave no declared key holding `key` is refused, "the power to declare keys, once lost, can be regained by no entry" [SPEC §7; CHARTER A2.5; `check.py` line 86] — the fourth maxim applied to the one act whose irreversibility would be total.

The record shows the mechanism used as intended. Genesis declared one key, `guy-master`, with four powers [seq 0]; it was re-declared with seven as C1 opened [seq 1] and with nine when the ledger's types arrived [seq 33]. The parties entered by declaration — builder, reviewer, counsel [seqs 6–8], each widened as the layer needed [seqs 31–34, 48–49] — and the herald, the process that merges, received `merge` and nothing else [seq 51; `herald-2`, seq 201]. When the herald's key moved from counsel's session to the sovereign's machine, the old key and a session-held builder key were revoked by declaring them with no powers [seqs 216, 217], and every entry those keys had signed remains valid, because recognition judged each by the law before it. Seventeen `key` entries in all [log@6ebea1a]. The keys are Dennis and Van Horn's capabilities and Miller's authority-as-reference (chapter 2 §2.13): a party that does not hold `merge` cannot merge, and there is no instruction anywhere that says it may not.

**What the law says** changes by amendment, and amendment is three acts and a wait [CHARTER A2.7; SPEC §10.12–13]. A `decision` of kind `transmute` names the amendment; the `amend` entry follows, carrying the SHA-256 of `CHARTER.md` with the amendment's text appended and an `activate_at` above its own seq; the amendment is in force from that height and never before; and between the `amend` and its height no `push` is lawful — "the law changes, then the code". The kernel records the promulgated charter and the schedule [`check.py` lines 94–95] and refuses an `amend` whose id is reused or whose height is not above its seq [line 71]; the judge enforces the rest, because it needs git: `charter_mismatch` if trunk's `CHARTER.md` does not hash to the promulgated charter, `amend_untransmuted` if an `amend` was not preceded by its `transmute`, `push_during_amendment` if a push falls in the wait [SPEC §10.2, §10.12–13]. The transmute-then-amend shape is Suber's (1990): an entrenched rule is first made mutable, as a separate move, and the two moves are two signed entries on the log. The price of an amendment is recorded in its own text [CHARTER A3.4, A4.5, A5.3] — the fifth amendment says it is the fifth in seventeen days and what the procedure ratio stood at that morning — and a forecast about whether it will ever bite is entered beside it [CHARTER A4.5: seq 60; A5.3: seq 121].

**What the code is** changes by `push`. The trusted base — the five paths of SPEC §10.1 — is digested over path and content, and a `push` entry signed by the master key names the digest of the trunk it authorises [SPEC §5, push; CHARTER A2.6]. The judge refuses a trunk whose digest is not the one in force, self-check included, so a change to the checker that no entry records turns `main` red [SPEC §10.11, `trusted_base_unrecorded`]. The record binds the code in the plain sense that every digest a push names is the digest of a commit on `main`: the author resolved all seven, and genesis's, to the first first-parent commit carrying each [`judge/judge.py:digest` over `git rev-list --first-parent main` @6ebea1a]:

## 3.4 Adjudication — the judge

The checker decides validity and nothing else can [CHARTER §3, Adjudication]. But the log alone cannot carry some facts the law needs — what the trusted base of a commit is, whether `CHARTER.md` hashes to the promulgated charter, whether a proposal's log is a byte extension of trunk's, which paths a commit touched — and these are the judge's [SPEC §10; `judge/judge.py:judge`]. The judge runs in CI on `pull_request_target`, so the workflow and the judge are trunk's whatever the proposal contains [`.github/workflows/judge.yml`; LAW.md §2.1]; it extracts trunk's kernel from the trunk *commit* into a temporary directory and runs that, never a checkout [`judge/judge.py:run_kernel`]; it runs the second checker likewise and refuses `checker_drift` on any disagreement [SPEC §10.5]; it holds no secret and a read-only token [CHARTER §9.6]. The proposal's code is never executed. Its entries are data.

The judge's grounds are fourteen, in order, each a refusal of the whole proposal [SPEC §10]. The first six are the record's: `trusted_path` (a digest differs, or `CHARTER.md` differs by a byte, or a non-regular file sits under a trusted path), `charter_mismatch`, `prefix_broken`, `genesis_by_proposal`, the kernel's own verdict with `checker_drift`, and `judge_from_proposal` (a `merge` naming a checker trunk does not have). Four are about the party and its scope, and they are the mechanism behind amendment A2.9, "review ends by construction": `unattributed_proposal` (no signed `proposal` entry names a commit of the proposal, or a commit after it touches more than `log.jsonl`), `party_scope`, `out_of_scope` and `code_cap`. The party is "the principal of the key that signed the last such `proposal` entry, under the law in force at it; the kernel has verified the signature, so the party is a fact, not a claim" [SPEC §10.7]. `judge/scope.json`, itself under a trusted path, assigns each party its prefixes: a builder may not touch the pins and vectors that judge it; a reviewer may propose only under `pins/` and `spec/vectors/`; counsel touches documents only [SPEC §10.8; CHARTER A2.9]. "Code enters from a builder, written to a text Guy has read; findings enter from a reviewer, as pins." The last four grounds apply to every judged log including trunk's own: `trusted_base_unrecorded`, `push_during_amendment`, `amend_untransmuted`, `decision_by_other` — the sovereign's acts are his, so a `decision` must be signed by a key declared in genesis [SPEC §10.11–14].

Every ground is decidable from git and the log alone, stated over powers and paths and never over a party's name, and refusing costs the proposer nothing but resubmission [CHARTER A2.3]. That clause is the standard against which any new ground is tested, and it is why the judge cannot become a reviewer: a ground that read the quality of code would fail the first test, and one that named a model would fail the second.

The code cap deserves a paragraph, because it is the one place where the judge counts and a reader might mistake the count for a judgement. `code_cap` refuses a proposal whose counted Python under the `counted` prefixes exceeds `judge/scope.json`'s `cap` [SPEC §10.10]. The cap is a resource constant: it is raised by a push at a window's opening, the push is the sovereign's, and the record says what it stood at and why — 3,000 at C0; 4,500 at C1's opening, 5,500 the same day, 6,200 at C1a's installing push, 6,900 at seq 197, 7,800 at seq 367, each raise a finding against the pre-statement that preceded it [SPEC §10, the paragraph before the scope block; seqs 5, 29, 197, 367]. The book will say in chapter 8 what those findings cost. Here the point is narrower: the cap enters no score and gates no merit; it is the court's budget line, and the judge enforces it the way it enforces everything else, by refusing.

## 3.5 The maxims as mechanisms

The charter's §2 states four maxims and says where each came from; chapter 2 argued why each is forced. This section records what each became.

**No one judges their own cause** (Coke, Dr Bonham's Case). Three mechanisms. The checker that decides an entry is fixed before the entry exists: trunk's kernel, by digest, run from trunk [§3.4]. A resolution's proposer differs from its forecast's: `self_judged`, judged by principal and not by key, in the kernel since C1a [`check.py` line 82; CHARTER A3.3; seq 29]. And the last judge of value is the world, through a judge no party can edit — the sealed judge of C3, which waits [CHARTER §8]. The maxim was extended to the sovereign by A2.8: the head hash of the log is published on every push, and a monitor he does not operate verifies that each head extends the last and that both checkers accept the log [CHARTER A2.8].

**The law looks forward and never commands the impossible** (Fuller; *lex non cogit ad impossibilia*). Forward: the fold [§3.2]; the amendment's wait [§3.3]; a `key` at *i* governs entries after *i*. The impossible, refused: a weak key [`sig.py:weak_key`] and the last `key` power [A2.5]. The witness rule — every rule admitted with a violating and a satisfying witness, the first proving it can fail and the second that compliance is possible — is written [CHARTER §3, Change] and waits for the first primary rule, which waits for the first case [CHARTER A2.1]. The book says so each time; the essay of 1 November said more than the record supports, and `plan.md` E1 records it.

**Whatever is held must be produced** (habeas corpus). The clerk, since C1b [`tools/clerk.py`, 88 lines]. Three writs, each derived from state and the clock and carrying a deadline: W1, every forecast entered after a window's opening, held by the principals who may resolve it, due at its `resolves_by`; W3, a `merge` on `main` whose commit had no green `tests` run before it; W4, every line of `status.py` that is not `met` [BRIEF-C1b §The clerk; `tools/enforcement.json`]. The escalation ladder is the charter's: re-invite; re-invite on another runner or model; writ to the sovereign [CHARTER §5]. The clerk decides nothing about validity and holds no change power; it is dumb and level-triggered, and the day it was not — when the obligation lived in counsel's head and four forecasts expired undischarged [seqs 45, 46, 47, 56] — is C1b's forcing witness. An item of the liveness statistic is a writ landing a timely act without the sovereign's hand [BRIEF-C1b §Liveness].

**Decide by expected value; forbid only the irreversible** (Arrow–Fisher). The master key's verbs and the last-key rule [§3.3]; refusal costs resubmission [A2.3]; windows that fail are followed, not patched [CHARTER §6]; wealth never reset [A4.1]. The corollary — every source of influence is scored, and no party acts except through entries that carry its identity — is `no_proposer`, `unknown_key`, `proposer_mismatch`, one blob one identity, and the judge's fingerprinting of a proposal's signers from the blobs and never from its claims [LAW.md §2.4; `judge/judge.py:fingerprint`]. Counsel's own key is on the log [seqs 8, 22, 31, 48], and its forecasts are scored with everyone's (chapter 6).

**Fuller's eight**, as the charter's table has them, with the code as it now stands:

| Fuller | check | where |
|---|---|---|
| generality | rules quantify over entry types, never name a party | `judge/scope.json` is keyed by party *role*; every ground is over powers and paths [A2.3] |
| promulgation | the charter's hash and the checker's digest are entries | genesis `charter` and `checker`; every `amend` and `push` [SPEC §5; `charter_mismatch`] |
| non-retroactivity | prefix interpretation, by construction | `check.py:check`, the fold; `activate_at` [SPEC §7] |
| clarity | every rule decidable, with its witnesses | SPEC §8 and §10 are decidable; witnesses wait for rules [A2.1] |
| non-contradiction | the satisfying witnesses pass the whole law together | waits for rules |
| possibility of compliance | each satisfying witness passes the law in force plus its rule | waits for rules; `bad_key` refuses the impossible now |
| constancy | change only by change entries; the rate is reported | five amendments in seventeen days, each pricing itself [A3.4, A4.5, A5.3] |
| congruence | the checker that runs is the one whose digest is recorded; two implementations agree | `trusted_base_unrecorded`; `checker_drift`; `tools/enforcement.json` rows `code` and `hand` |

The last row is the one to dwell on. Congruence between declared rule and official action is the principle a prompt-based harness cannot have, because the model that reads the rule is the party it binds. jack's enforcement map says, row by row, whether a principle is enforced by code or by hand, and C1b's criterion 7 required the rows it moved to read `code` [`status.py --subject C1b … @6b800e14`, "map" lines]. Two rows still read `hand`: that no party acts except through entries, enforced by sessions rather than code; and the election of proposers, which had no witness before C2 [`tools/enforcement.json`]. The map is how the book will say, at each layer, how much of the law was law.

## 3.6 The law changing under itself

A constitution that has never been amended has not been tested. jack's has been amended five times, and the five are the strongest evidence this chapter has, because none was planned, each was forced by something the record had shown, and each went through the procedure the text prescribed for it. They are listed here as cases, with the witness that forced each, what it changed, and the entries.

**A1 — C0 is the record (14 October).** Before the log existed. The first build of C0 carried the law language — stratified Datalog rules as data, witnesses, lapse, 658 kernel lines [REPORT.md §1, as transcript] — and counsel's review found it premature: no precedent needed a rule, and the charter's own §3 said primary rules accrete from cases. The sovereign cut C0 to the record only, moved the language to C1, and set the kernel's bound at 450 [CHARTER A1.1, A1.3, A1.5]. The amendment is in the charter text that genesis hashes [seq 0]; its witness was a kernel two fifths larger than it needed to be, and its recorded lesson is that "every layer is reviewed by a party that did not write it" [A1.7].

**A2 — the opening of C1 (18–19 October).** The first amendment entered by the amendment path: `decision transmute A2` [seq 3], `amend A2` with `activate_at` 5 [seq 4], the installing push at seq 5. Its witnesses were two cold reads of C1's brief and counsel's research of the same day [CHARTER A2, preamble]. It settled ten things, of which four are structural: the law language enters only when a first case arises, and if none has by C2's exit the thesis that three secondary rules suffice is on trial [A2.1]; `ts` does not decrease, in the kernel, binding every entry [A2.2]; the sovereign's acts are entries — a change to the trusted base is lawful only when a `push` names its digest, and veto, promotion, budget, grant and transmutation are `decision` entries [A2.6]; and amendment is two acts and a wait [A2.7]. Its recorded lesson is the one every later amendment obeys: "questions of what the charter allows are put to Guy as rulings and recorded here", and "whatever counsel and builders are forbidden is what the agent of C3 is forbidden" [A2.10].

**A3 — the ledger before the clerk (24–25 October).** `transmute A3` [seq 28], the installing push [seq 29], `amend A3` active from 31 [seq 30]. The witness was an argument rather than a defect — "the clerk is better built against a real obligation than an invented one, and an overdue forecast is the first such obligation the record can hold" — put to the sovereign as options and ruled on [CHARTER A3.1; `transcripts/RULING-20261025-ledger-first.md`]. It reordered the build, split C1 into two pre-stated windows, put the first maxim into the kernel as `self_judged`, and, being the third amendment in eleven days, applied §12's guard on procedure growth to itself: the C1a report was to count object entries against procedure entries and stop the layer above 5 : 1 [A3.4]. That count is now a line `status.py` prints every window.

**A4 — §6 corrected (26–27 October).** `transmute A4` [seq 66], `amend A4` active from 68 [seq 67]. The witness was a defect in the charter's own mathematics, found by counsel's literature check: §6 as written restarted the e-process at each new window, "which is *k* draws at one bound" [CHARTER A4, preamble; `transcripts/LITERATURE-20261026.md` item 2]. The amendment was cut three times by two cold reads of two model families to what they left standing [`transcripts/REVIEW-A4.md`, `-v2.md`, `-v3.md`], and what remained is the statistics chapter 2 §2.7 states: the wealth is never reset; *p*₀ is committed, never estimated from the window it judges; the bet is a function of the prefix with no further constant; comparisons are bets on a bounded difference. The rules the earlier versions tried to add went to a brief, to return "by amendment only after one of them has refused or decided an act". A4 entered a forecast about itself — p 0.5 that it is cited or refuses an act by 26 January 2027 [seq 60] — which is to say the amendment bet on its own necessity and will be scored.

**A5 — a window is a maximum (30 October).** `transmute A5` [seq 136], `amend A5` active from 138 [seq 137]. The witness was the record: every pre-stated criterion of C1a held on the prefix of 29 October, and A3's text — "runs fourteen days" — held the window open to 8 November with nothing left for it to measure; the sovereign's budget entry had named fourteen days as a maximum, and the text had made it a term [CHARTER A5, preamble; seq 50]. The amendment made a window end at the earlier of its stated end and the sovereign's `promote`, which may be entered only once every criterion holds on the current prefix, and made the stated end the `resolves_by` of the window's promotion forecast [A5.1–2]. It was the fifth amendment in seventeen days, it recorded the procedure ratio at 2.1 : 1 that morning, and it carried a forecast [seq 121]. The next day it was used: `decision promote C1a` closed that window on day six of fourteen [seq 188], and the day after that `decision promote C1b` closed the next on day two [seq 337].

Five cases; five witnesses; the same procedure each time from A2 on. Two patterns are worth stating because a referee will ask. First, the amendments move in one direction: each removes something from the law or from a layer's plan (a rule language, a term, a reset, a design in anticipation) rather than adding to it, and the one that adds a kernel rule, A3, adds the first maxim. Second, each amendment prices itself and bets on itself, so that the constitution's own changes are entries on the ledger it governs. The procedure count that guards against the court becoming its own object is applied to the amendments too.

## 3.7 What the law does not yet contain

The honest inventory. No primary rule exists; no rule language, no witness, no lapse, no notice period [CHARTER §3, Change; A2.1]. Recognition's clause (c), "every rule in force at its parent accepts it", holds vacuously [SPEC §7, last paragraph]. The thesis that three secondary rules suffice is therefore on trial, and the trial has a verdict date: if no case has arisen by C2's exit, C2's report says so [A2.1]. Two rows of the enforcement map read `hand` [§3.5]. The code cap has moved four times against pre-statements [§3.4]. The clerk's writ to the sovereign — the top of the escalation ladder — has not yet been needed, which is the point, and also means it is untested except by its pins. And the charter's lapse rule, by which law that has outlived its necessity falls away unless defended, cannot operate until there is law of that kind to lapse.

None of this is hidden; all of it is in the court's own texts. The book's claim for this chapter is not that the law is complete. It is that what exists is exactly the three rules, in 450 lines, that it has changed itself lawfully five times, and that everything it lacks is written down as lacking, with the condition under which it arrives.

## 3.8 What would show this chapter wrong

A reason code the kernel raises that is not in the table of §3.2, or a refusal path in `check_entry` the table does not cover: either means the chapter has not read the kernel it claims to have read. The count is fourteen and the author walked the file; appendix A lets the reader walk it too.

A primary rule found to be in the kernel after all — a check on conduct rather than on validity. The candidate is `self_judged`, and the chapter's answer (§3.5) is that it is a rule about what counts as a valid resolution, placed in recognition by amendment and said to be so. A referee who reads it as a conduct rule has an argument, and the book should meet it rather than wave it away.

An amendment that did not follow the path — an `amend` without its `transmute`, or a push in the wait — on the log. The judge's grounds make this a red `main` [SPEC §10.12–13], and the author checked the five pairs [seqs 3–4, 28–30, 66–67, 136–137].

A push whose digest matches no commit on `main`. The table of §3.3 resolves all eight; a reader can repeat it with `judge/judge.py:digest` over the first-parent history.

And the one that cuts deepest: a first case arising that recognition does not refuse, answered by a rule written into the kernel rather than entering as a precedent with witnesses. That would not show the chapter wrong about the law as it stands; it would show the programme abandoning the thesis the chapter is built on, and chapter 8 would have to say so.
